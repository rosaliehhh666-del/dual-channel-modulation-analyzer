### 记录 #2　插值频率位宽缺陷（14bit 左移归零 + 32bit 乘法溢出）
- 日期/阶段：2026-10-07 · FFT 频率插值
- 问题：三点插值频率公式 (($signed({1'b0,final_bin_hold})<<<16)+delta_q16)*ADC_FS_HZ>>>... 中，14bit 左操作数做 <<<16 后结果仍是 14bit（高位被截断归零），且后续 32bit 乘法溢出，导致 interp_freq_packed 输出垃圾值——会拖垮 UI 频率显示、自动测试判频和锁相 FCW 三个下游模块。
- Prompt（还原要点）："插值频率算出来是错的，怀疑是位宽问题：bin<<16 之后乘 Fs 会溢出，怎么改成正确的定点链？"
- 模型回答（要点）：给出固定位宽链：① bin_q16 = k*65536 + delta 用 32bit 有符号；② 符号扩展为 64bit（{{32{interp_bin_q16[31]}}, interp_bin_q16}）；③ freq_product = interp_ext * ADC_FS_HZ_64（64×64）；④ freq_result = freq_product >>> (16+LOG2_N+DECIM_LOG2)（算术右移 29）；⑤ 取 [31:0]。并强调 delta 用组合限幅值而非寄存器值，避免使用上一拍陈旧数据。
- 验证：数学复核成立：(k+δ)×Fs/2^LOG2_N，8192 点下最大频率 32.5MHz 不溢出；新版综合通过，代码注释标注 "V6: properly sign-extended interpolation result"。
- 纠错点：Verilog 中 <<< 不自动扩位——移位前先按最终位宽符号扩展；定点乘法先算好最大动态范围再定位宽，避免 32bit 溢出被静默截断。
### 记录 #3　THD 组合除法 + 全展开开方导致面积爆炸（place 失败）
- 日期/阶段：2026-10-06 · THD 模块
- 问题：THD 用组合逻辑 64bit 除法 + 全展开 64bit 开方，综合后 THD 模块约 15883 LUT，Place 失败。
- Prompt（还原要点）："THD 模块面积 15883 LUT 太大，place 过不了，怎么降面积？"
- 模型回答（要点）：组合除法/开方在 FPGA 上面积巨大，改为多周期迭代方案：恢复除法 64 拍（thd_divider_64，共享）+ 恢复开方 32 拍（isqrt_u64），用状态机（ST_DIV → ST_SQRT → ST_DONE）串行计算；FFT 一帧周期约 126μs，参数计算完全不必单周期完成，多周期对吞吐无影响。
- 验证：旧版副本工程重写后 synth → impl → write_bitstream 全部通过；整体 LUT 15000/20800（含 FFT 等全部逻辑）；新版 v6.1 继续沿用该方案，综合 0 Errors。
- 纠错点：FPGA 上"一个周期算完除法/开方"是面积杀手；凡一帧才更新一次的参数计算都应改为多周期状态机 + 共享运算单元。
### 记录 #4　THD 近似开方方案数值不可信（leading-one 近似不成立）
- 日期/阶段：2026-10-07 · THD 模块
- 问题：早期 THD 用 leading-one 位近似计算 psum/p1 的平方根比例，抽查发现数学不成立：shift=3 时结果为 0（真值 16）、shift=4 时结果为 64（真值 16）、shift=7 时结果为 1（真值 2）——仅 psum 最高位恰好为 27 时碰巧正确，数值不可信。
- Prompt（还原要点）："THD 用 leading-one 近似算出来的比值是错的（给了几个反例），这个近似能不能成立？"
- 模型回答（要点）：承认近似不成立，改回精确公式 THD_x100 = sqrt(psum * 1e8 / p1)（(10000)²=1e8 的缩放技巧）：64/64 多周期除法得 psum×1e8/p1，再经 32 拍 isqrt 开方；量纲验证：失真 100% 时输出 10000，正常信号 <1000。
- 验证：v6.1 公式与位宽推导写入头部注释（36×27=63bit 乘积不溢出 64bit 除法）；综合通过。
- 纠错点：数值算法上线前必须用边界反例验证（0/64/大数）；近似公式要给出误差界，给不出就换精确实现——"碰巧正确"和"数学正确"要分清。
### 记录 #5　THD 四项边界保护（谐波越界 / DC / 除零 / ±1 bin）
- 日期/阶段：2026-10-06 · THD 模块
- 问题：THD 谐波累积存在越界与除零风险：基波太靠近 Nyquist 时第 5 次谐波 5k±1 超出 FFT 半谱范围仍会访问；基波为 DC（bin≤1）或基波功率为 0 时公式无意义。
- Prompt（还原要点）："THD 上线前要加哪些边界保护？谐波越界、DC、除零分别怎么挡？"
- 模型回答（要点）：给出四项保护：① fund_bin*5+1 <= HALF_N（5 次谐波越界 → THD invalid）；② fund_bin >= 2（排除 DC）；③ 基波功率 p1 != 0（防除零）；④ 谐波窗口 spectrum_bin+1 >= k && spectrum_bin <= k+1（3-bin 窗且 k 越界时不访问）；无效通道输出 0xFFFF 哨兵。
- 验证：四项条件保留至 v6.1（ok_hold 逻辑），综合通过；0xFFFF 哨兵被 auto_tester 的 thd_ok 正确判失败。
- 纠错点：频谱算法上线前先枚举索引越界/除零/空输入三类故障；用哨兵值（0xFFFF）统一表达"无效"，下游判 valid 而非判数值。

### 记录 #8　相位差：双通道各找峰值导致 bin 错位
- 日期/阶段：2026-10-07 · 相位测量
- 问题：双通道各自独立找 peak bin 时，噪声可能让 CH0 peak=126、CH1 peak=127，此时两通道在不同频率点取相位，相位差无意义。
- Prompt（还原要点）："两通道各找各的峰值，噪声下 bin 错一位相位差就不对了，怎么处理？"
- 模型回答（要点）：改用公共基波 bin：以 CH0 峰值 bin 为公共 fundamental bin，CH1 在同一个 k 上读取复数（ref_ch1_re/im），双通道同频点 atan2 求差；并补 ±180000 mdeg 归一化（>+180° → -360°、<-180° → +360°，33bit 中间量防溢出）；V7 再加 low-signal 有效性门控（相位功率低于噪声底时 invalid）。
- 验证：xfft_frame_2ch 增加 is_ref_bin 捕获逻辑；phase_measurement 输出经 wrap 后 ∈[-180000,+180000]；综合通过。
- 纠错点：相位测量必须在同一频率点比较；先对齐 bin，再谈相位；测量类算法要配"信号太弱时输出无效"的门控，而不是硬给数值。
### 记录 #9　插值 δ 无限幅导致无意义频率
- 日期/阶段：2026-10-07 · 频率插值
- 问题：三点插值公式 δ=0.5·(Pk-1-Pk+1)/(Pk-1-2Pk+Pk+1) 在异常谱线下可能得到 δ=3.7 这类越界值，导致频率结果无意义。
- Prompt（还原要点）："插值 δ 异常大怎么办？要不要限幅？"
- 模型回答（要点）：对 δ 做 ±0.5 bin 限幅：Q16 定点下 delta_clamped 限制在 ±32768（±0.5）；同时除法器对负数做了符号处理（分子/分母取绝对值 + 符号位恢复），限幅用组合逻辑直接由除法结果算出，避免陈旧寄存器。
- 验证：V6 插值链中 delta_clamped 生效，freq_result 输出稳定；综合通过。
- 纠错点：抛物线插值的前提是"峰值确实在邻域内"；越界 δ 直接说明峰值搜索或谱线异常，限幅是兜底不是掩盖——还要同时看峰值搜索是否可靠。

### 记录 #12　Hann 窗接口位宽适配与 BRAM 开销评估

> 【后续纠正】“Hann最大增益0.5”和“锁相加窗必然不适用”不能作为通用结论。实际截位需按系数缩放、输入范围和舍入策略核对；后续全速锁相实例已启用Hann，必须验证有限窗增益、相位与积分条件。保留下面回答作为早期建议，不作为当前规格。

- 日期/阶段：2026-10-07 · V7 创新包集成
- 问题：新增 Hann 窗（8192 点 Q15 系数 ROM）输出 16bit，但 xfft_frame_2ch 输入样例为 12bit，直接级联位宽不匹配；系数 ROM 资源占用需评估。
- Prompt（还原要点）："Hann 窗 16bit 输出怎么接 xfft_frame_2ch 的 12bit 输入？BRAM 够不够？"

### 记录 #30　CNN 幅值校准 LUT：5 级流水线 + fail-closed 安全机制

> 【资格边界】数字幅值LUT不等于模拟电压/相位校准完成，默认无效与回退是保护，不是模型质量证书。

- 日期/阶段：2026-10-08 · AI 测量保真
- 问题：CNN 去噪后幅值会有系统性偏差（网络学到的增益不一定是 1.0），直接送测量链路会导致 Vpp/RMS/THD 全部偏移。

- 纠错点：校准模块必须 fail-closed 而不是 fail-open；默认值应该是"无效"而不是"增益 1.0"；下游判决模块必须检查校准有效标志，不能假设校准永远正确。

- 模型回答（要点）：不是 RTL 问题，是**测试台自身的采样竞争**。原 TB 用 `@(posedge clk)` 驱动激励，与 DUT 的 posedge 捕获沿同沿；同时监视器也在 posedge 采样内部信号，读到的 `frame_id` 是上一帧的残留值（日志显示 `tj=100 fid=14`），据此做出的归因完全错误。解法：激励改为 **negedge 驱动**、监视改为 **negedge 采样**——两者都避开 DUT 的捕获沿，且 negedge 时上沿的 NBA 结果已稳定，读数确定可信。
- 验证：改后 6 项故障注入全部通过（有效信号间断 / 超量程 OTR / flush / job_id 不匹配 / 索引错序 / 故障后回 IDLE），正常窗口导出完整：**21 META + 63 PARAM + 256 TRAIN_INPUT + 256 ADC_RAW + 257 wave（含 1 条 `wave:nan,nan` 间隔）+ 232 TRAIN_PRED + 1 END，共 42,955 字节**。
- 纠错点：测试台的**驱动沿与采样沿必须避开 DUT 捕获沿**（推荐统一 negedge）。更重要的元教训：当"监视结果与预期不符"时，**先怀疑监视方法，再怀疑被测对象**——错误的观测手段会制造出看起来很像 RTL bug 的假象，AI 在这一轮就差点据此下错误结论。

### 记录 #38　激励计数器位宽不足导致窗口内回绕，被误判为"丢点"
- 日期/阶段：2026-10-18 · 数字链路仿真
- 问题：PC 侧校验报 `index 250→251: 跳变 −255（期望 +1）`，初看是 ADC 丢点或通道错位。
- Prompt（还原要点）："ADC_RAW 序列中间突然掉 255，是丢点还是通道交换？"
- 模型回答（要点）：都不是，是**激励本身的位宽回绕**。TB 里 ADC 斜坡取 `ramp[7:0]`（8 位），而导出窗口跨 **512 个时钟周期**，8 位计数器必然在窗口内回绕。第二个坑：`adc_sample` 相对 `ramp` 滞后一拍，开窗瞬间抓到的是清零前的残留值（表现为首点为 262、其后从 0 开始），同样会被判成不连续。解法：位宽从 8 位扩到 **11 位**（> log2(窗口跨度)），并在开窗前清零、再等 4 拍让一级流水追上。
- 验证：改后 `adc_ch0 = [2,3,4,5,...]`、`adc_ch1 = [-2,-3,-4,-5,...]` 严格连续且互为相反数；`verify_raw.py` 11 项检查全通过（含"CH0 严格递增无重复无遗漏""两路未交换 ch1 == -ch0"）。
- 纠错点：设计激励时，**计数器位宽必须大于 log2(窗口跨度)**；信号有流水延迟时要在开窗前等待稳定。"看起来像丢点/错序"的异常，先排除激励自身的回绕与相位问题，再归因到 DUT。

### 记录 #39　文本串口协议没有 CRC：能力边界误判与 PC 侧验收工具链建立
- 日期/阶段：2026-10-18 · 协议与验收方法
- 问题：AI 曾把"CRC 验收"列为当前文本串口协议可完成项。
- Prompt（还原要点）："当前活动版的文本串口能做 CRC 校验吗？"
- 模型回答（要点）：**不能**。当前活动版 `v32_vofa_uart.v` 是 VOFA+ FireWater **文本行协议**，字段包含 `frame_id`/`index`/统计量/波形数值，但**没有任何 CRC 字段**。因此只能验证：字段完整性、点数、索引单调、帧号连续、帧边界——**不能检出任意比特翻转**（例如 "1234" 变成 "1334" 无法发现）。要做 CRC 验收必须使用带 CRC 的协议版本及其配套接收器，两者不可混用。
- 配套动作：为此建立不依赖硬件的 PC 侧验收工具链
  - `tools/vofa_text.py`：FireWater 文本协议解析器（`parse_file` → `(frames, FrameStats)`）
  - `tools/verify_raw.py`：结构与序列验收（11 项），支持 `--expect-adc-ramp` 与 `--json` 报告
  - `tools/ref_math.py`：与 RTL 定点规则对齐的软件参考（统计量 / Hann / FFT / DDC / 正弦拟合）
  - `sim/tb_adc_capture.v`：ADC 采集链路仿真（CH0 递增 / CH1 递减，两路未交换、无重复无遗漏、OTR 标记正确、锁定丢失后重新预热）
  - 已对齐的定点规则：`mean = Σx >> LOG2_N`（算术右移=向下取整）、`vpp = max−min`、`RMS_AC = isqrt((N·Σx² − (Σx)²) >> 2·LOG2_N)`（先移后开方）、Hann 为 Q15 且 `(x·c) >>> 15`、FFT 输入先 `<<4` 且每级蝶形 `>>1`（总归一化 1/N）
  - 自检：1 MHz / 500 counts 正弦 → `vpp=1000`、`rms_ac=353`（=500/√2）、拟合 `f=999847 Hz`、`amp=499.76`、`R²=0.9997`、DDC `amp=499.84`
- 纠错点：**协议能力必须逐字段核对源码**，不能按"一般协议都有 CRC"想当然。更要区分两件独立的事：**数字正确性**（同 RAW 下 FPGA 与软件参考是否一致）与**模拟采样质量**（RAW 与参考仪器测到的输入是否相符）——数字一致不代表没有模拟失真、噪声或混叠。

### 记录 #41　新增 V32CAP3 二进制上传口（带 CRC32），补齐文本协议无 CRC 的缺口

> 【集成边界】此处为新增上传口的仿真、综合与布线证据，不是RK3506端实时接收/屏幕验收；较早采样归档采用相同应用协议，也不能替代新口板测。

- 日期/阶段：2026-10-19 · RAW 上传通道
- 问题：文本协议无 CRC（见记录 #39），无法满足"数据完整性"验收；同时需要把双通道 RAW 送给 Linux 侧做波形重建与显示。
- Prompt（还原要点）："需要一个能把 RAW 完整传出去、并且能验完整性的接口，怎么设计？"
- 模型回答（要点）：新增**二进制上传口 V32CAP3**，与 VOFA 文本口物理独立、可同时工作：
  - 帧长恒定 **16428 字节**：8 B 魔数 `"V32CAP3!"` + version(3) + frame_id + adc_fs_hz(65 MHz) + decimation(1) + points_per_channel(**4096**) + flags(0) + start_index(64 bit) + 16384 B 样点 + 4 B CRC32
  - 样点为 **int16 小端交错**（CH0 在 `40+4i`、CH1 在 `42+4i`），4096 点/通道
  - **CRC32**：反射多项式 `0xEDB88320`、初值 `0xFFFFFFFF`、最终异或 `0xFFFFFFFF`，**只覆盖 `[0, 16424)`**（头部 40 B + 全部样点），尾部 4 字节自身不参与；校验向量 ASCII `"123456789"` → `0xCBF43926`
  - 单帧内 4096 点**真正连续**（`t(i) = i / 65e6`），帧间是死区（采样窗口仅 63 µs，传输 178 ms）
  - 单向，无 ACK / 无命令通道 / 无帧尾
  - 引脚 **AB5** → RK3506 的 UART RX，两边必须共地；AB6（VOFA 文本口）保持不动
- 验证：① 仿真出 2 帧 32856 字节，`check_frame.py` 判定"合格 2 帧，问题 0 处"，`frame_id 1→2`、`start_index 0→184794`（无重叠），激励 `ch1 = ~ch0` 负值符号扩展全部正确；② 综合 `u_v32cap3` 644 单元、**4 块 BRAM**（4096×2×16 bit = 16 KB 样点 FIFO），黑盒 0；③ 实现后 **WNS +1.410 ns / WHS +0.053 ns，0 违例端点（42,529）**，未布线网络 0，DRC 0 Error / 0 Critical；④ 物理层反查 `v32_tx → IOB_X1Y29 → AB5`，与 base_v1 落在同一 site。
- 纠错点（规格书点名的最易错四处）：① 12 位样点必须**符号扩展**到 16 位（−13 要发 `F3 FF`，不是 `F3 0F`）；② CRC 只覆盖前 16424 字节；③ `points_per_channel = 4096` 不是 8192；④ **帧长必须精确 16428**，多一字节就会让下一帧的魔数错位。另：给 AI 的提示词里应写明"不要发明协议里没有的字段"。
